## 결정과 이유

- **결정**: 차량 데이터 접근을 `VehiclePort` 인터페이스로 격리. **대안**: 앱이 `VSSManager`를 직접 호출. **이유**: `VSSManager`는 compileOnly라 외부에서 실행 불가. 인터페이스 뒤에 Fake를 두면 외부에서 앱 전체가 실제로 돈다. **되돌릴 조건**: 없음(사내 머지 리스크의 핵심).
- **결정**: 스텁을 별도 모듈(`vss-stub`)에 두고 사내에선 모듈 자체를 뺀다. **대안**: 앱 모듈 안에 스텁 소스. **이유**: 시스템 jar와 스텁이 동시에 있으면 duplicate class. 모듈이면 `include` 한 줄로 끄고 켠다.
- **결정**: Kotlin + Compose. **대안**: Java + View (가이드 예제와 동일). **이유**: 두 에이전트 모두 Compose 생산성이 높고, 스텁만 Java로 두면 시그니처 위험은 없다.
- **결정**: 에이전트 분담은 **레이어별 소유권**(Claude: 빌드·VSS·상태기계·문서·리뷰 / Codex: 화면·기능·테스트). **대안**: 구현자/리뷰어 교차, 단계별 순차. **이유**: 파일 소유가 갈리면 충돌이 적고, 사내 머지 접점(빌드·VSS)을 한 에이전트가 끝까지 책임진다.
- **결정**: GitHub은 private. **이유**: 사내 문서에서 파생된 API 계약이 들어 있다. 사내 스크린샷과 에뮬 이미지는 `.gitignore`.

## 막힌 것과 해결

- **Bash 히어독 스크립트가 통째로 실패** → 긴 히어독 안의 따옴표 파싱 오류로 아무것도 안 만들어짐 → 파일마다 Write 도구로 개별 생성 → **교훈**: 한글이 섞인 여러 파일은 히어독 한 방보다 파일 단위 쓰기가 안전.
- **단위 테스트에서 `mobis.vss` 못 찾음** → `compileOnly`는 테스트 클래스패스에 안 들어감 → `val vssApi`를 `compileOnly`와 `testImplementation` 양쪽에 → **교훈**: "한 줄 교체" 원칙을 지키려면 변수로 묶어야 한다.
- **에뮬 화면 캡처가 텍스트 파일로 저장됨** → PowerShell `>` 리다이렉트가 바이너리를 UTF-8로 변환 / Git Bash에선 `/sdcard`가 `C:/Program Files/Git/sdcard`로 경로 변환 → `MSYS_NO_PATHCONV=1` + `screencap -d <display-id>`(에뮬이 디스플레이 2개) → **교훈**: Windows에서 adb는 Git Bash + 경로 변환 해제가 제일 덜 아프다.
- **속도 숫자가 검은색으로 안 보임** → Compose에서 `Surface` 없이 `Box`+`background`를 쓰면 content color가 적용되지 않음 → `Surface(color, contentColor)`로 감싸기.

## 배운 것

- 리스크는 "정보 부족"이 아니라 "외부에서 실행 불가"다. 계약이 문서화돼 있으면 스텁은 정확히 만들 수 있다.
- 사내 머지 접점을 **두 줄**(vssApi, USE_FAKE_VSS)로 줄여 놓으면 나머지 전부를 외부에서 마음껏 바꿀 수 있다.
- 동료가 준 에뮬은 "사내 환경"이 아니라 "화면 크기가 같은 순정 AAOS"였다. 확인하지 않았으면 Real 경로를 외부에서 테스트하려고 시간을 썼을 것이다.
